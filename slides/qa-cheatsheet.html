The one they'll definitely ask
Doesn't Intune already have audit logs? Confident
Yes — and that's exactly the point to make yourself before they do. Intune already has solid audit logs — you can see who clicked what, after the fact. The problem isn't that we lack logs; it's that they're reactive. No peer review before a change ships, no diff, no linked ticket for why, and no git revert when you need to undo fifteen settings in thirty seconds.
Is this a new tool you built? Confident
No — say so upfront, it builds credibility with this crowd. We didn't build a new tool. IntuneCD already does the heavy lifting and is a well-known community project. What we built is the pipeline around it — guardrails, rings, and a live demo of the whole loop, which almost nobody shows end to end.
Architecture & security
Is this OIDC / Workload Identity Federation? Honest gap
No — static client secret, and that's fine to admit. Today it's a rotated client secret, scoped to least-privilege Graph permissions, stored as a GitHub Actions secret — not hardcoded. OIDC federation is the obvious next hardening step.
Do you have automated drift detection / auto-revert? Honest gap
No — recovery is a human-triggered git revert, not a scheduled job. Right now drift recovery is a human running git revert and re-applying — what you watched in Act 6. A scheduled drift-check job that pages someone is the natural next layer, not built yet.
What about Graph API rate limits (429s)? Honest gap
Two devices in this demo never gets close to throttling — say that plainly. At this demo's scale — two devices — we've never hit a 429. At fleet scale the answer is standard retry with exponential backoff; happy to point you at Microsoft's Graph throttling docs after.
Is there an approval gate before promoting Pilot-Ring to Prod-Ring? Honest gap
No auto-promotion exists — rings today are two separate, independently-assigned groups. Today Pilot-Ring and Prod-Ring are just two separately-assigned groups — promotion is a deliberate second commit, not an automated gate with health checks. That gate is the natural next step.
Scope & platform breadth
Does this work for macOS / Jamf too? Different stack
Different MDM vendor, same pattern. Different MDM, same underlying pattern — Jamf has its own API and its own community tooling equivalent to IntuneCD. The guardrail-plan-apply-ring shape transfers; the tool doesn't.
What about BYOD / MAM (app-only management)? Out of scope
Different object model entirely — don't overclaim. This demo is MDM, full device enrollment. MAM/BYOD is app-level only, different Graph objects, different policy shape — same GitOps principle would apply, haven't demoed it.
What about Autopilot / enrollment itself as code? Out of scope
Deliberately out of scope tonight. Out of scope for this talk, but a natural next step — Autopilot profiles are Graph objects too, the same pipeline shape would cover them.
What about co-management / ConfigMgr (SCCM)? Out of scope
Real nuance exists, keep the answer short. Co-managed workloads add another layer — some settings are still arbitrated by ConfigMgr until a workload is switched over. This demo assumes Intune owns compliance and configuration outright.
Why not just use Intune's built-in policy versioning? Confident
It isn't policy-as-code — no admission control, no plan step, no tie to your org's existing review process. Intune's version history shows you what changed inside the portal — it doesn't gate the change before it ships, doesn't run a guardrail check, and isn't tied to your org's existing PR review process the way git is.
Do giant .intunewin app packages go in git too? Confident
No, deliberately. No — those are multi-gigabyte binaries and belong in dedicated packaging/artifact storage. What's in git is exactly what's lightweight and text-based: compliance policies, configuration profiles, scripts.
Demo mechanics (if someone's paying close attention)
Why run everything by hand instead of letting GitHub Actions trigger it live? Confident
Deliberate reliability choice — already flagged proactively in Act 1. This exact sequence — guardrail, dry-run plan, apply via Graph — already runs as real GitHub Actions on every PR and merge to this repo. I'm running each step by hand on stage so a flaky venue network or a cold runner doesn't eat our time.
Why does the portal show "compliant" when Graph just showed noncompliant? Confident
Known, expected lag — not a bug, reinforces your own thesis. The portal's device dashboard runs on a separate, slower reporting pipeline. Graph API is the live ground truth — which is exactly why we query it directly instead of trusting a cached UI.
