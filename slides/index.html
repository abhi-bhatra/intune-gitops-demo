Section 01

The Problem

How Windows device policy gets managed today - and why it doesn't scale past a handful of laptops.

Timing: 30 sec transition slide. Let it breathe, don't rush into the next slide.

The problem

Sound familiar?

Silent fleet-wide mistakes

One wrong click in the Intune portal can disable BitLocker or block USB storage for every enrolled device - instantly, with no review.

Audit logs are a security camera, not a guardrail

Intune does log who clicked what - after the fact. No diff, no linked ticket, no review before it ships, no "undo" - just raw property deltas and a timestamp to reconstruct from.

No diff before it ships

There's no "plan" step - you find out what changed by watching devices break, not by reading a diff first.

Rollback is... memory

The only undo button is someone remembering exactly what the settings used to be.

Timing: 2-3 min.

Anchor each card in something the audience has felt in a Kubernetes/infra context - manual kubectl edits in prod, no PR review, no `kubectl diff`. The point: Windows fleet management today is where infra was before IaC.

The pipeline

Git commit to device compliance, in 5 steps

Git Commit

Policy change as reviewable JSON, like a Deployment manifest

Guardrail

Policy-as-code check, local - rejects bad shapes before CI starts

CI Plan

IntuneCD dry-run diffs against the live tenant - no writes yet

CD Apply

Merge to main pushes the policy for real, via Microsoft Graph

Device Reports Back

Compliant / noncompliant status flows back from the real device

Timing: 2-3 min. This is the backbone diagram - refer back to it mentally during the whole demo.

Point out step 2 explicitly: the guardrail never talks to the tenant. It's a pure local check, same mental model as an admission controller.

Show me the code

The guardrail, in ~10 lines of Python

guardrails/validate_policy.py 
@rule("Windows compliance policies must enforce a minimum OS build")
def must_enforce_os_minimum_version(doc, path):
    if doc.get("@odata.type") == "#microsoft.graph.windows10CompliancePolicy":
        if not doc.get("osMinimumVersion"):
            return f"{path}: osMinimumVersion not set"
    return None

The gotcha

The catch nobody warns you about

MDM sync channel — minutes

osMinimumVersion, most settings — reports back on the regular device check-in. This is the lever we used live.

Device Health Attestation — hours

BitLocker, Secure Boot, Code Integrity — graded by an async cloud attestation pipeline, fully decoupled from the sync channel above.

Timing: 2-3 min. This is the "war story" slide - the thing that took multiple debugging sessions to root-cause.

Tell it as a story: "We originally tried to demo this live with BitLocker. It took us several sessions to figure out why the device just never came back to compliant - turns out it wasn't broken, it was just on a reporting channel that can take hours." This is the kind of detail that makes a talk memorable.

Takeaways

3 lessons from running this for real

Guardrails catch mistakes early

A bad shape never reaches the tenant - caught before CI even runs.

Rings contain blast radius

Canary-style assignment means one bad rollout affects one ring, not the fleet.

Know your signal latency

Not every setting reports instantly - async attestation pipelines need a different playbook.
